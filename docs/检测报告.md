## 3. 检测范围与方法

1. **静态检查**：`compileall` 编译全部 Python 模块；抽取前端内联脚本做 `node --check`；扫描源码与配置中的明文口令/密钥；核对 `.gitignore` 覆盖运行库与缓存。
2. **接口自动化**：五个阶段脚本用 `TestClient` 进程内启动，各自注入隔离临时库与 mock 模型，覆盖表结构、状态机、双人复核、harness、前端联调。
3. **黑盒运行时**：真实 `uvicorn` 起服务，用独立 HTTP 客户端逐项探测鉴权、越权、统一响应结构、脱敏、审计链、页面可达性与延迟。
4. **性能基线**：对版本列表接口连续采样 20 次，取 P95 与最大值。

## 7. 缺陷记录

### KB-001　知识库短词检索返回空结果（已修复）

| 项目 | 内容 |
| --- | --- |
| 严重级别 | 中（影响可用性，不影响数据安全） |
| 发现方式 | 黑盒检测第 17 项：检索「薪酬」返回 0 条，检索「薪酬调整」返回 1 条 |
| 根因 | FTS5 `trigram` 分词器按 3 字符切分，检索词短于 3 个字符时 `MATCH` 永远无命中，且代码未对短词降级 |
| 修复 | `app/kb.py`：新增 `use_fts = _fts_available(conn) and len(q) >= 3`，短词直接走 `LIKE` 子串匹配；附「为什么这么卡」注释说明割裂体验 |
| 复测 | 「薪酬」命中 1 条、「职级」命中 1 条、「现场调研」命中 2 条；阶段②知识库断言仍 ALL PASS |
| 回归风险 | 低。短词走 `LIKE` 无相关度排序（`score=0.0`），结果集较小场景可接受；长词仍走 bm25 排序 |

## 8. 安全专项结论

| 控制点 | 设计 | 实测 |
| --- | --- | --- |
| 身份认证 | HMAC-SHA256 签名令牌，`token_secret` 仅来自环境变量 | 伪造令牌、错误口令均 401；缺失密钥启动即失败 |
| 角色隔离 | 服务层 `require_roles` 依赖，前端隐藏按钮不作为权限依据 | 经办人访问审计 403；复核人创建版本 403 |
| 双人复核 | 复核人 ≠ 经办人、一人一次、必须两签才能生效，且由数据库触发器兜底 | 自复核、重复复核、单签生效全部被拦截 |
| 数据脱敏 | 非管理员金额与差额均为 `****`；审计只存载荷摘要 | 7 个样本全脱敏；管理员才见明文 |
| 审计完整性 | 逐条哈希链，前序哈希串联 | 31 条链完整，可定位篡改点 |
| 模型边界 | 端点限本机/私网白名单，结论必须人工确认 | 配置白名单生效；`WAIT_CONFIRM` 状态不可直接提交 |
| 统一响应 | 所有出口经 `ok()/fail()` 与全局异常处理器 | 成功/失败/参数错/404 结构一致 |

## 10. 遗留风险与建议

| 风险 | 影响 | 建议 |
| --- | --- | --- |
| 本次检测使用 `mock` 模型 | 未验证真实千问的 JSON 遵循度与超时行为 | 接本地 vLLM/Ollama 后补一轮 `APP_LLM_MODE=http` 检测，重点看 `LLM_BAD_JSON` 与事务持锁时长 |
| 调研调用在写事务内 | 慢模型会长时间持有 SQLite 写锁 | 生产前把模型调用移出事务，只保留结论落库的短事务 |
| 免登录演示入口 `ui.auto_login_actor` | 开启时等价于跳过口令 | 生产必须置空；如需演示仅允许回环地址访问 |
| SQLite 单写者 | 高并发复核会排队等锁 | 迁 Postgres，保持 SQL 语义不变 |
| 令牌无吊销 | 过期前一直有效 | 引入短 TTL + 服务端会话表 |
| 列表无分页 | 数据量增大后响应体膨胀 | 增加 `limit/offset` 与前端分页 |
