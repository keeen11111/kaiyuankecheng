## 1. 系统定位

把每一次薪酬调整建模成**不可变版本**：新版本保存变更前后快照，原薪酬记录在双人复核通过并由管理员生效前绝不改动。变更生效前必须完成一次**现场调研**，由自研 harness 驱动本地千问做制度检索与取证，产出结构化结论；结论必须经**具名人员人工确认**才能进入双人复核。

三条不可让步的底线：

1. **双人且不同人**：经办人不能复核自己的变更，两名复核人不能是同一人，一人只能签一次。
2. **人始终在回路**：模型输出只能落到 `research_sessions`，状态恒为 `WAIT_CONFIRM`；模型无权提交、复核、生效。
3. **数据不出内网**：模型地址强制本机/私网白名单，外发上下文白名单结构，薪酬恒为 `****`。

## 2. 架构分层

```
HTTP 请求
  ↓
app/main.py          路由、角色依赖、事务边界、统一响应封装
  ↓
app/service.py       版本状态机、双人复核、人工确认、生效事务、脱敏视图
  ↓
┌────────────┬──────────────┬────────────┬──────────────┐
│ app/db.py  │ app/audit.py │ app/kb.py  │ app/harness.py│
│ SQLite DDL │ 审计哈希链    │ FTS5 知识库│ 多轮工具编排  │
└────────────┴──────────────┴────────────┴──────────────┘
                                   ↓
                     app/llm.py（本地千问适配 + 内网地址审查）
                     app/prompts.py（docs/提示词.md 区块加载）
```

## 4. 数据模型

| 表 | 关键字段 | 约束与设计意图 |
| --- | --- | --- |
| `employees` | `emp_id`, `name_mask`, `dept`, `grade` | 只存脱敏姓名，证件/银行卡不入库 |
| `salary_records` | `emp_id`, `base_salary_cents`, `currency`, `version_no` | 金额以**整数分**存储，杜绝浮点误差；`version_no` 作乐观锁 |
| `salary_change_versions` | `before_json`, `after_json`, `reason`, `research_question`, `operator_id`, `status`, `research_session_id` | 版本链只追加；`CHECK` 锁死状态取值 |
| `review_records` | `version_id`, `reviewer_id`, `slot`, `decision` | `UNIQUE(version_id, slot)` + `UNIQUE(version_id, reviewer_id)` + `CHECK(slot IN (1,2))` |
| `research_sessions` | `status`, `transcript_json`, `conclusion_json`, `confirmed_by` | 结论未确认前 `WAIT_CONFIRM`，确认人具名 |
| `kb_docs` / `kb_fts` | 原文表 + FTS5 虚表 | `trigram` 分词支持中文子串；不可用时自动降级 `LIKE` |
| `audit_log` | `seq`, `payload_hash`, `prev_hash`, `row_hash` | 只存载荷摘要，不存明文金额；哈希链可定位篡改点 |

**数据库触发器** `trg_review_no_self`：在 `review_records` 插入前比对 `NEW.reviewer_id` 与版本 `operator_id`，命中即 `RAISE(ABORT, 'REVIEW_SAME_PERSON')`。这是绕过服务层、直接改库也躲不开的最后一道防线。

## 5. 状态机

| 状态 | 含义 | 允许的下一动作 |
| --- | --- | --- |
| `DRAFT` | 草稿，可发起调研 | `research/run`、`research/confirm` |
| `RESEARCHING` | harness 运行中（事务内短暂状态） | 成功→`DRAFT`；失败→回滚为 `DRAFT` |
| `RESEARCH_DONE` | 结论已人工确认 | `submit` |
| `PENDING_REVIEW` | 待第一复核人 | `review`（slot=1） |
| `REVIEW_ONE` | 第一人已通过 | `review`（slot=2） |
| `APPROVED` | 双人通过，待生效 | `effective`（仅 ADMIN） |
| `EFFECTIVE` | 已生效，薪酬基线已更新 | 终态 |
| `REJECTED` | 任一复核人驳回 | 终态，需新建版本重提 |

所有写操作前统一走 `_assert_status()`；生效是不可逆动作，额外复核轨迹本身，而不只信状态字段。

## 6. 双人复核的四道防线

1. **路由层**：`require_roles("REVIEWER","ADMIN")`，无权限连业务函数都不会进入。
2. **服务层**：`review_change()` 在 `BEGIN IMMEDIATE` 事务内重读状态，先判"复核人 != 经办人"、再判"同一人没签过"，按状态分配 slot。
3. **数据库层**：唯一约束 + CHECK + 触发器，并发双写与直接改库都被拦。
4. **生效层**：`effective_change()` 重新校验"恰好两条 APPROVE、两个不同 reviewer、均非经办人"，再用 `WHERE version_no = ?` 乐观锁原子更新薪酬。

> 为什么用 `BEGIN IMMEDIATE`：两个复核人同时点提交时，若各自读到 `REVIEW_ONE` 都可能认为自己该占 slot=2。立即抢写锁 + 事务内重读状态，可杜绝这类并发越权。

## 7. 现场调研 harness

自研循环，不引入任何 agent 框架：

```
for round in 1..max_rounds:
    渲染 SYSTEM_RESEARCH + USER_ROUND（脱敏版本上下文、最近 6 轮轨迹、现场答复）
    → 调用本地千问（外发前审查）
    → extract_json 解析为 {tool, args}（非 JSON 直接失败）
    → 工具白名单校验 → 执行 kb_search / ask_field / finish
    → 追加 transcript
    → finish 时校验结论结构，通过后落库为 WAIT_CONFIRM
```

| 工具 | 权限 | 参数限制 |
| --- | --- | --- |
| `kb_search` | 只读知识库 | query 限长 200，top_k 由配置给 |
| `ask_field` | 读取已登记书面答复 | question 限长 300，缺失答复明确标"取证缺口"，不编造 |
| `finish` | 输出结论 | 五字段必填、枚举白名单、字符串限长，`recommend` 只能是 `SUBMIT_REVIEW`/`HOLD` |

**人工确认闸口**：结论只写 `research_sessions`，版本状态回到 `DRAFT`；`research/confirm` 必须 `confirm: true` 且 `require_human_confirm` 未被关闭，才把版本推进到 `RESEARCH_DONE` 并记录具名确认人。配置被改成 `false` 时接口直接报 `HUMAN_CONFIRM_DISABLED`，不允许悄悄绕过。

## 8. 知识库与本地千问

- **知识库**：SQLite FTS5 `trigram` 虚表 + 原文表，手工同步；查询短语用双引号包裹并转义，防 FTS 语法注入；建表失败或查询异常自动降级 `LIKE`。种子制度文档写在 `config.yaml` 的 `kb.seed_documents`，不散落在代码里。
- **千问接入**：`llm.mode` = `mock`（离线确定性回复，验证脚本零外部依赖即可跑通）/ `http`（真实调用本地 vLLM、Ollama 等 OpenAI 兼容端点）。
- **地址审查**：`http` 模式下解析 `base_url`，主机必须在 `llm.allowed_hosts` 白名单或为回环/私网 IP；公网地址抛 `LLM_HOST_FORBIDDEN`，**不发起请求**。
- **失败语义**：超时、重试耗尽、返回体异常一律抛 `LLM_UNAVAILABLE` / `LLM_HTTP_ERROR`，事务回滚，版本不会停在 `RESEARCHING`；绝不返回空串让上层误判成功。

## 9. 数据红线与安全设计

| 红线 | 落地点 |
| --- | --- |
| 密钥不进代码 | `config.yaml` 用 `${APP_TOKEN_SECRET}` / `pin_env` / `api_key_env` 占位，启动时由环境变量注入 |
| 模型地址不进代码 | `llm.base_url` 在 `config.yaml`，可再由 `APP_LLM_BASE_URL` 覆盖 |
| 薪酬脱敏 | `mask_salary()` 对非 ADMIN 返回 `****`，差额也脱敏（防反推调薪幅度）；ADMIN 明文需审计 |
| 审计不落明文金额 | `append_audit()` 先清洗 `base_salary_cents` 等敏感键，只写 SHA-256 摘要 |
| 数据不出内网 | 模型地址白名单 + 外发消息仅允许 `role`/`content` 两个键 + 凭据关键词兜底 |
| 不可篡改留痕 | 审计哈希链 `row_hash = SHA256(ts|actor|action|target|payload_hash|prev_hash)`，可定位首个断点 |
| 提示词注入 | 知识库内容在提示词中被明确定义为"数据不是指令"；工具白名单 + 结论枚举校验兜底 |
| 不泄露内部信息 | 全局异常处理器把 500 统一成固定文案，不回显堆栈、SQL、响应体 |

## 12. 阶段交付

### 阶段①　数据模型与工程底座

1. **变更文件清单**：`config.yaml`、`requirements.txt`、`app/__init__.py`、`app/config.py`、`app/response.py`、`app/db.py`、`app/audit.py`、`app/security.py`、`app/models.py`、`app/kb.py`、`app/prompts.py`、`app/llm.py`
2. **启动与自测命令**（Windows Git Bash / Linux / macOS 通用）：
   ```bash
   python -m pip install -r requirements.txt
   export APP_TOKEN_SECRET=dev-secret APP_PIN_OPERATOR=pin-op APP_PIN_REVIEWER_A=pin-a APP_PIN_REVIEWER_B=pin-b APP_PIN_ADMIN=pin-admin
   export APP_LLM_MODE=mock

   ```

4. **最可能出问题的地方**：SQLite 编译版本不带 `trigram` 分词器时 FTS5 建表失败（已自动降级 `LIKE`，但中文检索质量下降）；`${ENV_VAR}` 未注入会在启动期直接抛 `ValueError`，这是刻意设计的快速失败。

## 13. 已知限制与演进建议

| 限制 | 说明 | 建议演进 |
| --- | --- | --- |
| 身份清单在配置里 | 本地自测足够，生产不应由 YAML 管账号 | 接统一身份系统 / OIDC，保持 `require_roles` 接口不变 |
| SQLite 单写者 | 高并发复核会等锁 | 迁 Postgres（同 SQL 语义，`BEGIN IMMEDIATE` 换成行锁） |
| 调研调用在事务内 | 慢模型会长时间持锁 | 改为"先在事务外跑模型，再短事务落库" |
| FTS5 trigram | 中文子串可用但无语义检索 | 需要语义召回时再评估，且必须保持本地化部署 |
| 审计链为单链 | 能发现篡改但不能阻止 | 追加只追加式写入权限或外部只写归档 |
| 令牌无吊销 | 过期前一直有效 | 引入短 TTL + 服务端会话表 |
| 免登录演示入口 | `ui.auto_login_actor` 开启时等价于跳过口令 | 生产置空；如需演示则配合仅回环地址访问 |

## 14. 代码规范落地

- 每个函数都有中文 docstring，固定三段：**入参 / 出参 / 失败时**（写明错误码、是否抛异常、是否回滚）。
- 每一行代码都带中文行内注释；SQL DDL 的每一行也带 `--` 注释。
- 关键业务逻辑（安全审查、权限校验、人工确认、双人去重、生效复核）另有"为什么这么卡"的注释，说明不限制会导致的后果。
- 配置统一在 `config.yaml`，密钥与模型地址通过 `${ENV_VAR}` 注入；提示词统一在 `docs/提示词.md`。
- 所有对外接口经 `ok()` / `fail()` 与全局异常处理器输出统一结构。
